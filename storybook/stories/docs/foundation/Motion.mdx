# Motion & Animation

NoorUI's motion system is built on a small set of purposeful animation tokens. Every transition and animation in the library is derived from these tokens, ensuring consistent timing across all components. The system also includes full `prefers-reduced-motion` support and RTL-aware animation handling.

## RTL Animation Awareness

Animations that use `translateX` need special attention in RTL layouts. In LTR, "forward" motion is left-to-right. In RTL, it is right-to-left. If a `translateX` value is not flipped, the animation moves in the wrong visual direction.

NoorUI handles this in two ways:

### 1. RTL Utility Overrides

For simple transforms, Tailwind's `rtl:` variant prefix is used to flip the value:

<CodeBlock
  filename="Switch toggle RTL handling"
  language="tsx"
  code={`{/* The switch thumb moves right in LTR, left in RTL */}
<span
  className={cn(
    "block h-4 w-4 rounded-full bg-background shadow-sm transition-transform",
    checked ? "translate-x-4 rtl:-translate-x-4" : "translate-x-0"
  )}
/>`}
/>

### 2. Directional Slide Animations

For slide-in animations, the direction is chosen based on context. A sidebar that slides in from the "start" side uses `slide-in-from-left` in LTR and `slide-in-from-right` in RTL. Components that need this typically accept a `side` prop and map it accordingly.

<DesignDecision title="translateX Always Needs RTL Consideration" type="warning">
  <p>
    Any animation or transition that uses <code>translateX</code> is directional and will appear visually reversed in RTL if not handled. When you write <code>translate-x-4</code>, always ask: "Should this flip in RTL?" If the answer is yes, add <code>rtl:-translate-x-4</code>. Vertical transforms (<code>translateY</code>) are not affected by direction and do not need RTL variants.
  </p>
</DesignDecision>

## Reduced Motion Support

NoorUI fully respects the `prefers-reduced-motion` media query. When a user has requested reduced motion in their operating system settings, all animations and transitions are effectively disabled:

<CodeBlock
  filename="styles/globals.css"
  language="css"
  code={`@media (prefers-reduced-motion: reduce) {
  *,
  *::before,
  *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
}`}
/>

<DesignDecision title="Why 0.01ms Instead of 0s?">
  <p>
    Setting <code>animation-duration</code> and <code>transition-duration</code> to <code>0.01ms</code> instead of <code>0s</code> ensures that JavaScript animation event listeners (<code>animationend</code>, <code>transitionend</code>) still fire. A duration of <code>0s</code> can cause these events to never trigger, which breaks component logic that depends on them -- for example, an accordion that waits for the close animation to finish before removing content from the DOM.
  </p>
  <p>
    The single <code>animation-iteration-count: 1</code> ensures infinite animations (like <code>shimmer</code>) run once and stop, rather than looping. Combined with the near-zero duration, the animation is imperceptible but still functionally complete.
  </p>
</DesignDecision>
