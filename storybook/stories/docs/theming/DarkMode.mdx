# Dark Mode

NoorUI implements dark mode through **class-based toggling** using Tailwind CSS v4's custom variant system. Each theme defines its own dark mode palette, ensuring consistent contrast and readability across all five visual identities.

---

## How It Works

### The Custom Variant

Dark mode is registered as a Tailwind v4 custom variant in `globals.css`:

<CodeBlock
  filename="styles/globals.css"
  language="css"
  code={`@custom-variant dark (&:where(.dark, .dark *));`}
/>

This tells Tailwind to generate `dark:` prefixed utilities that activate when the `.dark` class is present on an ancestor element (or the element itself). The `:where()` pseudo-class keeps specificity flat, preventing cascade conflicts.

### Toggling Dark Mode

At runtime, dark mode is toggled by adding or removing the `dark` class on `document.documentElement`:

<CodeBlock
  filename="Implementation"
  language="typescript"
  code={`// Toggle dark mode
document.documentElement.classList.toggle('dark', mode === 'dark');

// Or explicitly set it
document.documentElement.classList.add('dark');    // enable dark mode
document.documentElement.classList.remove('dark');  // enable light mode`}
/>

### Integration with next-themes

In the Next.js application, NoorUI integrates with `next-themes` for automatic system preference detection and persistence:

<CodeBlock
  filename="Storybook preview.tsx"
  language="tsx"
  code={`import { ThemeProvider } from 'next-themes';

// In the decorator:
<ThemeProvider
  attribute="class"         // Uses class-based toggling (not data-attribute)
  defaultTheme={mode}       // 'light' or 'dark'
  forcedTheme={mode}        // In Storybook, forces the selected mode
  enableSystem={false}       // Storybook manages mode via toolbar
>
  {children}
</ThemeProvider>`}
/>

The `attribute="class"` setting ensures `next-themes` adds/removes the `.dark` class rather than a `data-theme` attribute. This is critical because our Tailwind custom variant and all theme CSS selectors rely on the `.dark` class.

### Storybook Integration

In Storybook, the decorator applies both the theme and mode simultaneously:

<CodeBlock
  filename="Storybook preview.tsx — decorator"
  language="typescript"
  code={`React.useEffect(() => {
  document.documentElement.setAttribute('dir', direction);
  document.documentElement.setAttribute('lang', locale);
  document.documentElement.classList.toggle('dark', mode === 'dark');
  applyThemeToDocument(theme);
}, [direction, locale, mode, theme]);`}
/>

## Dark Mode per Theme

Each of the five themes defines its own dark mode palette through specific CSS selectors. This means dark mode is not a one-size-fits-all inversion -- each theme's dark variant is individually crafted.

### Default Theme

The default theme's dark mode is defined in the `.dark` block, overriding the `:root` variables:

<CodeBlock
  filename="Default dark mode"
  language="css"
  code={`.dark {
  --background: 222.2 84% 4.9%;
  --foreground: 210 40% 98%;
  --card: 222.2 84% 4.9%;
  --card-foreground: 210 40% 98%;
  --primary: 239 84% 67%;
  --primary-foreground: 222.2 84% 4.9%;
  --muted: 217.2 32.6% 17.5%;
  --muted-foreground: 215 20.2% 65.1%;
  --border: 217.2 32.6% 17.5%;
  --input: 217.2 32.6% 17.5%;
}`}
/>

### Named Theme Dark Variants

Each named theme uses a compound selector (`.theme-*.dark`) to define its dark overrides:

<CodeBlock
  filename="Theme-specific dark selectors"
  language="css"
  code={`/* Minimal dark */
.theme-minimal.dark {
  --color-background: hsl(0 0% 10%);
  --color-foreground: hsl(0 0% 95%);
  --color-card: hsl(0 0% 12%);
  --color-muted: hsl(0 0% 20%);
  --color-border: hsl(0 0% 20%);
  /* ... */
}

/* Futuristic dark — subtle shift from an already-dark base */
.theme-futuristic.dark {
  --color-background: hsl(240 10% 5%);
  --color-foreground: hsl(0 0% 98%);
  --color-card: hsl(240 10% 8%);
  --color-muted: hsl(240 10% 12%);
  --color-border: hsl(240 10% 15%);
  --color-success: hsl(160 84% 50%);
  --color-info: hsl(199 89% 58%);
}

/* Cozy dark — warm earth tones preserved in dark mode */
.theme-cozy.dark {
  --color-background: hsl(25 15% 12%);
  --color-foreground: hsl(35 20% 95%);
  --color-card: hsl(25 15% 15%);
  --color-muted: hsl(25 10% 20%);
  --color-border: hsl(25 10% 25%);
  --color-success: hsl(152 69% 50%);
  --color-warning: hsl(27 96% 65%);
  --color-info: hsl(201 65% 60%);
}

/* Artistic dark — deep blacks with warm-tinted surfaces */
.theme-artistic.dark {
  --color-background: hsl(0 0% 8%);
  --color-foreground: hsl(40 20% 95%);
  --color-card: hsl(0 0% 10%);
  --color-primary: hsl(280 60% 60%);
  --color-muted: hsl(0 0% 15%);
  --color-border: hsl(0 0% 18%);
  --color-success: hsl(158 64% 50%);

/>

<DesignDecision title="The Futuristic theme is already dark-optimized" type="warning">
  <p>
    The Futuristic theme's <strong>light mode is itself dark</strong>. Its base background is
    <code>hsl(240 10% 8%)</code> -- a near-black blue-tinted surface. The <code>.theme-futuristic.dark</code>
    variant only deepens this slightly to <code>hsl(240 10% 5%)</code> and adjusts status colors for even
    more contrast. This is intentional: the Futuristic theme is designed for dark environments (dashboards,
    control panels, data visualization). If you need a truly light Futuristic theme, consider creating a
    custom variant.
  </p>
</DesignDecision>

## Status Colors in Dark Mode

Status colors (success, warning, info) require special attention in dark mode. On a light background, these colors need to be deep and saturated for visibility. On a dark background, the same colors need to be lighter to maintain contrast against the dark surface.

## Using Dark Mode in Components

### Prefer Semantic Tokens

The best approach is to use semantic tokens that automatically adapt to dark mode. When you write `bg-background` or `text-foreground`, these utilities resolve to the correct value for both light and dark modes without any `dark:` prefix:

<CodeBlock
  filename="Recommended: semantic tokens"
  language="tsx"
  code={`// These utilities auto-adapt to dark mode through CSS custom property resolution
<div className="bg-background text-foreground border-border">
  <p className="text-muted-foreground">Secondary text</p>
  <span className="text-success">Status: Active</span>
</div>

// Card surfaces automatically have correct contrast
<div className="bg-card text-card-foreground rounded-lg border p-4">
  Card content that works in any mode
</div>`}
/>

### When to Use `dark:` Prefix

Use the `dark:` prefix only when you need mode-specific behavior that cannot be expressed through semantic tokens:

<CodeBlock
  filename="Occasional: explicit dark overrides"
  language="tsx"
  code={`// When you need mode-specific static colors
<div className="bg-white dark:bg-neutral-900">
  Static color that doesn't use semantic tokens
</div>

// When you need mode-specific opacity or visual weight
<div className="shadow-md dark:shadow-lg dark:shadow-black/20">
  Shadows need more intensity in dark mode to be visible
</div>

// When you need mode-specific decorative elements
<div className="border-t border-gray-200 dark:border-gray-800">
  Decorative divider with specific gray values
</div>`}
/>

<DesignDecision title="Prefer semantic tokens over dark: prefix">
  <p>
    Every <code>dark:</code> prefix is a maintenance burden. It doubles the number of utility classes
    on an element and creates two places where a color decision lives. Semantic tokens like
    <code>bg-muted</code> and <code>text-foreground</code> resolve to the correct value in any mode
    because the underlying CSS custom property changes. Reserve <code>dark:</code> for genuinely
    mode-specific concerns like shadow intensity, decorative borders, or the rare case where no
    semantic token exists for your need.
  </p>
</DesignDecision>

## Dark Mode Resolution Order

The full resolution chain for a dark mode value in a themed context:

<CodeBlock
  filename="Resolution cascade"
  language="text"
  code={`1. :root                     → --primary: 239 84% 67%
2. @theme                    → --color-primary: hsl(var(--primary))
3. .theme-cozy               → --color-primary: hsl(25 85% 55%)     ← theme override
4. .dark                     → --primary: 239 84% 67%               ← default dark (same)
5. .theme-cozy.dark          → (no primary override)                 ← keeps .theme-cozy value

Result in .theme-cozy.dark:  --color-primary = hsl(25 85% 55%)  (Cozy's warm orange)`}
/>

Notice that if a `.theme-*.dark` block does not override a particular property, the value from the `.theme-*` light block is retained. Themes only need to define dark overrides for properties that actually change between modes -- typically backgrounds, surfaces, borders, and status colors. Primary and secondary brand colors often remain consistent across modes.
