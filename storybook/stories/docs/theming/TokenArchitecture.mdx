# Token Architecture

NoorUI's theming is powered by a **3-layer token system** that flows from raw CSS custom properties through Tailwind registration to theme overrides. Understanding these layers is essential to customizing or extending the design system.

---

## The Three Layers

### Layer 1: Raw CSS Custom Properties

The foundation layer defines all design tokens as CSS custom properties in the `:root` block (light mode) and the `.dark` block (dark mode). These values use **raw HSL components without an `hsl()` wrapper**:

<CodeBlock
  filename="styles/globals.css — :root"
  language="css"
  code={`:root {
  /* Core palette — raw HSL values, no hsl() wrapper */
  --background: 220 13% 99%;

  --primary: 239 84% 67%;
  --primary-foreground: 210 40% 98%;
  --secondary: 174 72% 56%;

<DesignDecision title="Why raw HSL values without the hsl() wrapper?">
  <p>
    Storing values as <code>239 84% 67%</code> rather than <code>hsl(239 84% 67%)</code> is intentional.
    It enables Tailwind's opacity modifier syntax. When you write <code>bg-primary/50</code>, Tailwind
    needs to inject the opacity value <em>inside</em> the color function:
    <code>hsl(239 84% 67% / 0.5)</code>. If the variable already contained the <code>hsl()</code> wrapper,
    this composition would be impossible. The raw format keeps the door open for alpha channel modifiers
    throughout the entire utility layer.
  </p>
</DesignDecision>

### Layer 2: Tailwind Registration

The `@theme` block in `globals.css` maps the raw CSS custom properties to Tailwind utility classes. This is where the `hsl()` wrapper gets applied:

<CodeBlock
  filename="styles/globals.css — @theme block"
  language="css"
  code={`@theme {
  /* Colors — semantic tokens via CSS vars */
  --color-background: hsl(var(--background));
  --color-foreground: hsl(var(--foreground));
  --color-primary: hsl(var(--primary));
  --color-primary-foreground: hsl(var(--primary-foreground));
  --color-secondary: hsl(var(--secondary));
  --color-secondary-foreground: hsl(var(--secondary-foreground));
  --color-destructive: hsl(var(--destructive));
  --color-destructive-foreground: hsl(var(--destructive-foreground));
  --color-muted: hsl(var(--muted));
  --color-muted-foreground: hsl(var(--muted-foreground));
  --color-accent: hsl(var(--accent));
  --color-accent-foreground: hsl(var(--accent-foreground));
  --color-popover: hsl(var(--popover));
  --color-popover-foreground: hsl(var(--popover-foreground));
  --color-card: hsl(var(--card));
  --color-card-foreground: hsl(var(--card-foreground));
  --color-border: hsl(var(--border));
  --color-input: hsl(var(--input));
  --color-ring: hsl(var(--ring));

  /* Semantic status colors */
  --color-success: hsl(var(--success));
  --color-success-foreground: hsl(var(--success-foreground));
  --color-warning: hsl(var(--warning));
  --color-warning-foreground: hsl(var(--warning-foreground));
  --color-info: hsl(var(--info));
  --color-info-foreground: hsl(var(--info-foreground));

  /* Border radius */
  --radius-lg: var(--radius);
  --radius-md: calc(var(--radius) - 2px);
  --radius-sm: calc(var(--radius) - 4px);

  /* Font families */
  --font-sans: 'Inter', system-ui, sans-serif;
  --font-arabic: 'IBM Plex Sans Arabic', sans-serif;
  --font-mono: 'JetBrains Mono', monospace;

  /* Shadows, animations, keyframes... */
}`}
/>

When Tailwind processes this block, it generates utilities like `bg-primary`, `text-foreground`, `border-border`, `rounded-lg`, etc. The `--color-*` prefix convention tells Tailwind v4 to create color utilities; `--radius-*` creates border-radius utilities; `--font-*` creates font-family utilities.

## The Cascade

The full resolution order for any color value is:

```
:root vars (Layer 1 - raw HSL)
  --> @theme registration (Layer 2 - hsl() wrapper for Tailwind)
    --> .theme-* class override (Layer 3 - resolved hsl() values)
      --> .theme-*.dark compound override (Layer 3 - dark mode within theme)
        --> Component uses bg-primary, text-foreground, etc.
```

When a component uses `bg-primary`, the browser resolves the value by walking this cascade. If a `.theme-cozy` class is present, `--color-primary` resolves to `hsl(25 85% 55%)` (warm orange). If only the default `:root` is active, it resolves to `hsl(239 84% 67%)` via the `@theme` block's `hsl(var(--primary))` reference (indigo).

<DesignDecision title="Why a 3-layer system instead of direct variable overrides?">
  <p>
    The 3-layer architecture serves distinct purposes. Layer 1 (raw HSL) enables Tailwind opacity
    modifiers on the default theme. Layer 2 (@theme) generates the utility classes that components
    actually reference. Layer 3 (theme overrides) provides direct <code>hsl()</code> values that
    take precedence over the <code>hsl(var(...))</code> references in Layer 2. This separation
    means the default theme gets maximum Tailwind flexibility (opacity modifiers work), while named
    themes get maximum control (direct color values, no indirection). It also means you can use
    Tailwind utilities like <code>bg-primary/50</code> in the default theme and they degrade
    gracefully in named themes.
  </p>
</DesignDecision>

## How Tokens Flow into Components

A component never references theme-specific values. It uses Tailwind utilities that resolve through the cascade:

<CodeBlock
  filename="Example component usage"
  language="tsx"
  code={`// This button works in every theme, every mode, every direction
<button className="bg-primary text-primary-foreground rounded-md px-4 py-2">
  Submit
</button>

// Opacity modifiers work on the default theme's raw HSL values
<div className="bg-primary/10 text-primary border border-primary/20 rounded-lg p-4">
  Highlighted section
</div>

// Status colors adapt per-theme automatically
<span className="text-success">Payment complete</span>
<span className="bg-warning/5 text-warning-foreground px-2 py-1 rounded">Pending</span>`}
/>

The key insight is that components are **theme-agnostic**. They reference semantic tokens (`primary`, `muted`, `success`) that resolve to different concrete values depending on which theme class is active. This is what makes the system extensible -- adding a new theme requires no changes to any component.
