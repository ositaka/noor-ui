# Technical Overview

NoorUI is a production-grade, bidirectional React component library. This page documents the full technology stack, build pipeline, provider hierarchy, and file structure that powers it.

---

## Tech Stack

| Layer | Technology | Role |
|---|---|---|
| **Runtime** | React 18+ | Component model, hooks, concurrent features |
| **Framework** | Next.js 15 (App Router) | Server components, routing, font optimization |
| **Language** | TypeScript | End-to-end type safety across components, tokens, and i18n |
| **Styling** | Tailwind CSS v4.1 | Utility-first CSS with CSS-first configuration |
| **Primitives** | Radix UI | Accessible, unstyled headless components |
| **Variants** | Class Variance Authority (CVA) | Type-safe variant definitions with Tailwind classes |
| **Icons** | @phosphor-icons/react | Flexible icon system with weight and color context |

---

## CSS-First Configuration

Tailwind CSS v4 eliminates `tailwind.config.ts`. All configuration now lives in CSS using the `@theme` directive.

<CodeBlock
  filename="styles/globals.css"
  language="css"
  code={`@import "tailwindcss";

@theme {
  --color-primary: hsl(var(--primary));
  --color-secondary: hsl(var(--secondary));
  --color-success: hsl(var(--success));
  --color-warning: hsl(var(--warning));
  --color-info: hsl(var(--info));
  --color-destructive: hsl(var(--destructive));
  --color-border: hsl(var(--border));
  /* ... all semantic tokens registered here */
}`}
/>

The PostCSS pipeline is minimal. Only `@tailwindcss/postcss` is used -- no legacy plugins, no autoprefixer (Tailwind v4 handles vendor prefixes internally).

<CodeBlock
  filename="postcss.config.js"
  language="js"
  code={`module.exports = {
  plugins: {
    '@tailwindcss/postcss': {},
  },
};`}
/>

<DesignDecision title="Why CSS-first over tailwind.config.ts?">
  <p>
    Tailwind v4's CSS-first approach means design tokens live alongside the styles they power. There is no context-switching between a JavaScript config file and CSS source. Theme overrides are pure CSS class selectors that override custom properties -- no JavaScript runtime, no re-renders, no build-time token generation step. The <code>@theme</code> block is the single source of truth for what Tailwind utilities exist.
  </p>
</DesignDecision>

## Provider Hierarchy

NoorUI uses a three-layer provider stack. The nesting order is intentional and must be preserved.

<CodeBlock
  filename="app/layout.tsx"
  language="tsx"
  code={`<DirectionProvider>           {/* 1. Outermost: manages dir, locale */}
  <ThemeProvider               {/* 2. next-themes: light/dark mode */}
    attribute="class"
    defaultTheme="system"
    enableSystem
  >
    <IconContext.Provider       {/* 3. Phosphor: default icon props */}
      value={{ weight: 'duotone', color: 'currentColor' }}
    >
      {children}               {/* App content */}
    </IconContext.Provider>
  </ThemeProvider>
</DirectionProvider>`}
/>

**DirectionProvider** is outermost because theme and icon providers may need direction context. **ThemeProvider** wraps icons because icon colors depend on the active theme's foreground tokens. **IconContext.Provider** is innermost, setting defaults that individual icons can override.

## Build Pipeline

NoorUI has three independent build targets.

### Component Build (tsup)

<CodeBlock
  filename="package.json (simplified)"
  language="json"
  code={`{
  "scripts": {
    "build": "tsup"
  }
}`}
/>

tsup bundles all component source into:
- **CJS** (`dist/index.js`) -- for Node.js and older bundlers
- **ESM** (`dist/index.mjs`) -- for modern bundlers with tree-shaking
- **Type declarations** (`dist/index.d.ts`) -- full TypeScript definitions

### CSS Build (@tailwindcss/cli)

<CodeBlock
  filename="CSS compilation"
  language="bash"
  code={`# Compiles styles/globals.css through Tailwind v4 → dist/styles.css
npx @tailwindcss/cli -i styles/globals.css -o dist/styles.css`}
/>

The output `dist/styles.css` contains all Tailwind utilities used by NoorUI components, all five theme definitions, light and dark mode variants, and the base reset.

### Storybook Build (@storybook/nextjs-vite)

Storybook uses the `@storybook/nextjs-vite` framework adapter, which leverages Vite for fast HMR and builds. The configuration includes custom stories globs, Vite path aliases matching the Next.js project, `react-docgen-typescript` for automatic prop table generation, and `addon-docs` and `addon-a11y` for documentation and accessibility auditing.

## File Structure

<CodeBlock
  filename="Project structure"
  language="text"
  code={`components/
  ui/                    # All UI components (button, card, dialog, etc.)
  providers/             # DirectionProvider and useDirection hook

lib/
  tokens.ts              # Theme config, applyTheme(), type exports
  utils.ts               # cn() utility (clsx + tailwind-merge)
  i18n.ts                # Centralized bilingual translations (~6000 lines)
  i18n/
    index.ts             # Re-exports from i18n.ts

styles/
  globals.css            # Tailwind v4 config, all themes, base styles
  package.css            # Distribution CSS (mirrors globals.css for npm)

storybook/
  .storybook/            # Storybook config (main.ts, preview.ts)
  stories/
    docs/                # MDX documentation pages
    components/          # Component stories (.stories.tsx)`}
/>

<DesignDecision title="Two CSS files: globals.css vs package.css">
  <p>
    <code>styles/globals.css</code> is the development file used by the Next.js app and Storybook. <code>styles/package.css</code> mirrors it for distribution via npm. This separation lets the development environment reference local font imports and Storybook-specific utilities without polluting the published package. The compiled output (<code>dist/styles.css</code>) is built from <code>package.css</code>.
  </p>
</DesignDecision>

## Storybook Configuration

<CodeBlock
  filename=".storybook/main.ts (simplified)"
  language="typescript"
  code={`const config: StorybookConfig = {
  framework: '@storybook/nextjs-vite',
  stories: [
    '../stories/**/*.mdx',
    '../stories/**/*.stories.@(js|jsx|ts|tsx)',
  ],
  addons: [
    '@storybook/addon-docs',
    '@storybook/addon-a11y',
  ],
  viteFinal: async (config) => {
    // Path aliases matching Next.js tsconfig paths
    config.resolve.alias = {
      '@/components': path.resolve(__dirname, '../../components'),
      '@/lib': path.resolve(__dirname, '../../lib'),
      '@/styles': path.resolve(__dirname, '../../styles'),
    };
    return config;
  },
  typescript: {
    reactDocgen: 'react-docgen-typescript',
  },
};`}
/>

The `react-docgen-typescript` integration automatically extracts prop types from component source files and renders them as interactive prop tables in Storybook docs pages. The Vite alias configuration ensures that `@/` path imports resolve correctly in the Storybook environment, matching the Next.js project's `tsconfig.json` paths.

<DesignDecision title="Why @storybook/nextjs-vite?" type="tip">
  <p>
    The <code>@storybook/nextjs-vite</code> framework adapter combines Next.js compatibility (App Router support, next/image, next/font) with Vite's fast build and HMR performance. This means Storybook understands Next.js conventions while starting up in seconds rather than minutes. It replaced the older Webpack-based <code>@storybook/nextjs</code> adapter.
  </p>
</DesignDecision>
