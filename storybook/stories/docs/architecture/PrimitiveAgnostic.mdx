# Primitive-Agnostic Design

NoorUI wraps every headless primitive behind its own stable API. This page explains why, how, and what trade-offs are involved.

---

## The Problem

Headless UI libraries ship breaking changes. Radix UI has renamed props, restructured component APIs, and changed default behaviors across major versions. Other libraries -- Headless UI, Ark UI, React Aria -- follow the same pattern. This is expected: headless libraries optimize for correctness and flexibility, not API stability.

But consumers of a design system should not care. When Radix renames `onOpenChange` to `onValueChange`, or restructures how `Dialog.Portal` works, every application using raw Radix imports must update. In a design system used across multiple products, this creates cascading migration costs.

---

## NoorUI's Abstraction

Every NoorUI component wraps its Radix primitive behind NoorUI's own props interface. Consumers never import from `@radix-ui/*` directly.

<CodeBlock
  filename="What consumers write"
  language="tsx"
  code={`// Consumers import from NoorUI, not from Radix
import { Dialog, DialogTrigger, DialogContent } from 'noorui-rtl';

// The API is NoorUI's contract, not Radix's
<Dialog>
  <DialogTrigger asChild>
    <Button>Open</Button>
  </DialogTrigger>
  <DialogContent>
    <p>Dialog body content</p>
  </DialogContent>
</Dialog>`}
/>

Internally, the Dialog component delegates to Radix primitives:

<CodeBlock
  filename="components/ui/dialog.tsx (simplified internals)"
  language="tsx"
  code={`import * as DialogPrimitive from '@radix-ui/react-dialog';

const Dialog = DialogPrimitive.Root;

const DialogContent = React.forwardRef<
  React.ElementRef<typeof DialogPrimitive.Content>,
  React.ComponentPropsWithoutRef<typeof DialogPrimitive.Content>
>(({ className, children, ...props }, ref) => (
  <DialogPrimitive.Portal>
    <DialogPrimitive.Overlay className={cn('fixed inset-0 bg-black/50 ...')} />
    <DialogPrimitive.Content
      ref={ref}
      className={cn(
        'fixed start-1/2 top-1/2 -translate-x-1/2 -translate-y-1/2',
        'bg-background border border-border rounded-lg shadow-lg',
        className
      )}
      {...props}
    >
      {children}
    </DialogPrimitive.Content>
  </DialogPrimitive.Portal>
));`}
/>

The consumer never sees `DialogPrimitive`. If Radix changes how `Portal` or `Overlay` work, NoorUI updates the internal implementation. The consumer's code does not change.

---

## The Contract

The component's **TypeScript props interface** is the contract. As long as the props signature and observable behavior remain stable, NoorUI can change anything inside the component.

<CodeBlock
  filename="The contract boundary"
  language="tsx"
  code={`// This is the contract. It does not mention Radix.
interface DialogContentProps {
  className?: string;
  children: React.ReactNode;
  onClose?: () => void;
}

// These are implementation details. They can change freely.
// - Which headless library is used (Radix, Ark, custom)
// - How the overlay is rendered
// - How focus trapping is implemented
// - Which CSS classes are applied internally`}
/>

<DesignDecision title="Props are the API, not the implementation">
  <p>
    This is the same principle behind any stable interface: define inputs and outputs, hide internals. NoorUI's props interfaces are the public API. The Radix dependency is an implementation detail. Consumers depend on the interface, not the primitive. This means NoorUI can upgrade Radix, swap to Ark UI, or even use custom primitives without breaking a single consumer import.
  </p>
</DesignDecision>

## CVA as the Variant Layer

Class Variance Authority (CVA) defines visual variants independently of the headless primitive. CVA produces a function that maps variant props to Tailwind class strings. It has no knowledge of Radix, React Aria, or any other library.

<CodeBlock
  filename="components/ui/button.tsx (CVA definition)"
  language="tsx"
  code={`import { cva, type VariantProps } from 'class-variance-authority';

const buttonVariants = cva(
  // Base classes — always applied
  'inline-flex items-center justify-center rounded-md text-sm font-medium transition-colors',
  {
    variants: {
      variant: {
        primary: 'bg-primary text-primary-foreground hover:bg-primary/90',
        secondary: 'bg-secondary text-secondary-foreground hover:bg-secondary/80',
        outline: 'border border-input bg-background hover:bg-accent',
        ghost: 'hover:bg-accent hover:text-accent-foreground',
        destructive: 'bg-destructive text-destructive-foreground hover:bg-destructive/90',
      },
      size: {
        sm: 'h-8 px-3 text-xs',
        md: 'h-10 px-4',
        lg: 'h-12 px-6 text-base',
      },
    },
    defaultVariants: {
      variant: 'primary',
      size: 'md',
    },
  }
);`}
/>

If NoorUI swaps Radix's `Slot` for a different polymorphic rendering approach, the CVA variants are unaffected. They are pure class string generation. If the underlying primitive changes how it renders the DOM, the Tailwind classes still apply the same visual output.

## The Slot Pattern

Radix's `Slot` component enables the `asChild` pattern for polymorphic rendering. Instead of rendering its own element, a component merges its props onto its child.

<CodeBlock
  filename="asChild usage"
  language="tsx"
  code={`// Without asChild: renders a <button>
<Button>Click me</Button>

// With asChild: renders an <a> with Button's styles
<Button asChild>
  <a href="/dashboard">Go to Dashboard</a>
</Button>`}
/>

This pattern is not Radix-specific. The `Slot` abstraction can be implemented independently (it is essentially `React.cloneElement` with prop merging). If NoorUI moves away from Radix, the `asChild` behavior is preserved by implementing or importing a compatible `Slot` utility. Ark UI, for instance, uses the same pattern.

<DesignDecision title="asChild is a design system concern, not a library concern" type="tip">
  <p>
    The <code>asChild</code> pattern exists because design systems need polymorphic components -- a Button that can render as a link, a Card that can render as an article. This need persists regardless of which headless library is used. NoorUI treats <code>asChild</code> as part of its own API contract, not as a Radix-specific feature.
  </p>
</DesignDecision>

## Future-Proofing

If Radix UI is deprecated tomorrow, NoorUI's migration path is contained:

1. **No consumer code changes.** Imports stay as `from 'noorui-rtl'`, not `@radix-ui/react-dialog`.
2. **Only internal files change.** Each component file swaps its `import * as Primitive from '@radix-ui/...'` to the new library.
3. **CVA variants are untouched.** The visual layer is decoupled from the primitive layer.
4. **TypeScript props remain stable.** The public interface does not reference Radix types.
5. **Tests validate behavior, not implementation.** Tests assert that a Dialog opens, focuses correctly, and closes -- not that it uses `DialogPrimitive.Root`.

---

## Trade-Off Acknowledged

This architecture adds a thin abstraction layer over Radix. Every NoorUI component file contains wrapper code that would not exist if consumers imported Radix directly.

The cost:
- Slightly more code per component (a `forwardRef` wrapper, `cn()` class merging, CVA integration)
- NoorUI must track upstream Radix changes and update wrappers when necessary
- Debugging requires looking through one more layer of code

The benefit:
- **API stability for consumers.** The most expensive thing in a design system is a breaking change that propagates to every consuming application.
- **Freedom to change internals.** NoorUI can upgrade, swap, or customize primitives without coordinating with consumers.
- **Consistent styling layer.** Every component goes through CVA and `cn()`, ensuring tokens, themes, and RTL support are applied uniformly.

<DesignDecision title="Stability over convenience">
  <p>
    For a design system serving multiple products in production, API stability is not optional -- it is the primary feature. A thin abstraction layer today prevents expensive, coordinated migration projects tomorrow. This is the same trade-off that every successful design system (Material UI, Chakra, Mantine) has made.
  </p>
</DesignDecision>
