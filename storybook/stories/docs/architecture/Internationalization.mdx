# Internationalization

NoorUI ships with a built-in bilingual translation system covering all component labels, descriptions, and UI strings in English and Arabic. This page documents the architecture, usage patterns, and rules.

---

## Architecture

All UI translations live in a single centralized file:

| File | Purpose |
|---|---|
| `lib/i18n.ts` | The translation source (~6000 lines, ~81K tokens). Contains the `content` object with `en` and `ar` branches. |
| `lib/i18n/index.ts` | Re-exports `content` from `i18n.ts` for cleaner import paths. |

The `content` object is a deeply nested TypeScript object with two top-level keys: `en` and `ar`. Both branches have an identical key structure -- every English key has a corresponding Arabic key at the same path.

<CodeBlock
  filename="lib/i18n.ts (structure)"
  language="typescript"
  code={`export const content = {
  en: {
    navigation: {

## The Pattern

Every component that displays text follows the same three-line pattern:

<CodeBlock
  filename="Standard i18n usage"
  language="tsx"
  code={`import { useDirection } from 'noorui-rtl';
import { content } from '@/lib/i18n'; // Internal: not exported from noorui-rtl

function MyComponent() {
  const { locale } = useDirection();
  const t = content[locale];

  return (
    <div>
      <h2>{t.myComponent.title}</h2>
      <p>{t.myComponent.description}</p>
      <Button>{t.button.submit}</Button>
    </div>
  );
}`}
/>

1. Get the current `locale` from `useDirection()` -- this returns `'en'` or `'ar'`.
2. Select the correct language branch: `const t = content[locale]`.
3. Access translations via dot notation: `t.section.key`.

When the user toggles direction (and by extension locale), the component re-renders and all text updates to the new language.

---

## The Forbidden Pattern

<DesignDecision title="Never use isRTL ternaries for text content" type="warning">
  <p>
    The pattern <code>isRTL ? 'Arabic text' : 'English text'</code> is <strong>forbidden</strong> for any string that appears in the UI. All user-visible text must come from the i18n system. Inline ternaries with hardcoded strings bypass the translation system, make text untraceable, and create a maintenance nightmare as the codebase grows.
  </p>
</DesignDecision>

<CodeBlock
  filename="Forbidden vs correct"
  language="tsx"
  code={`// WRONG: hardcoded text in component
const { isRTL } = useDirection();
<Button>{isRTL ? 'إرسال' : 'Submit'}</Button>

// WRONG: locale ternary with inline strings
<h2>{locale === 'ar' ? 'لوحة التحكم' : 'Dashboard'}</h2>

// CORRECT: use the i18n system
const t = content[locale];
<Button>{t.button.submit}</Button>
<h2>{t.navigation.dashboard}</h2>`}
/>

## Acceptable `isRTL` Usage

The `isRTL` value from `useDirection()` is appropriate for layout logic, CSS classes, and locale-dependent formatting -- anything that is not display text.

<CodeBlock
  filename="Valid isRTL usage"
  language="tsx"
  code={`const { isRTL, locale } = useDirection();

// CSS classes for directional layout
<div className={cn('flex', isRTL && 'flex-row-reverse')}>

// Alignment props that depend on direction
<Tooltip align={isRTL ? 'start' : 'end'}>

// Locale parameter for Intl formatting
const formatted = new Intl.NumberFormat(isRTL ? 'ar-SA' : 'en-US').format(price);

// Animation direction
<motion.div initial={{ x: isRTL ? 100 : -100 }} animate={{ x: 0 }}>

// Icon mirroring
<ArrowRight className={cn(isRTL && 'rotate-180')} />`}
/>

The rule is simple: `isRTL` controls **how** content is presented (layout, positioning, formatting). The i18n system controls **what** content is presented (text, labels, descriptions).

## Per-Category Translations

The translation structure mirrors the component library's category organization. Each component or feature area has its own section within the `content` object.

<CodeBlock
  filename="Translation structure by category"
  language="typescript"
  code={`content.en = {
  // Component categories
  navigation: { ... },
  button: { ... },
  dialog: { ... },
  card: { ... },
  form: { ... },
  table: { ... },

  // Feature areas
  auth: { ... },
  dashboard: { ... },
  settings: { ... },

  // GCC-specific
  hijriDate: { ... },
  prayerTimes: { ... },
  zakatCalculator: { ... },

  // AI components
  chat: { ... },
  streaming: { ... },
  modelSelector: { ... },
};`}
/>

This organization means you can find a component's translations by navigating to its matching key in the `content` object. If you are working on the Dialog component, its translations are at `content[locale].dialog`.

## TypeScript Workaround

The `content` object's deep nesting occasionally causes TypeScript union type inference issues. When the compiler cannot resolve which branch (`en` or `ar`) is being accessed, it may produce type errors on deeply nested properties.

The workaround is an explicit cast at the component level:

<CodeBlock
  filename="TypeScript deep nesting workaround"
  language="tsx"
  code={`const { locale } = useDirection();

// If TypeScript complains about deep property access:
const componentT = content[locale].zakatCalculator as any;

// Then use it normally
<h2>{componentT.title}</h2>
<p>{componentT.description}</p>
<label>{componentT.fields.goldWeight}</label>`}
/>

This is a pragmatic trade-off. The `as any` cast loses type checking on the translation keys, but the alternative -- generating discriminated union types for 6000+ lines of nested translations -- adds significant complexity for minimal runtime benefit. The translations are tested by rendering the components in both locales.

<DesignDecision title="Pragmatism over type purity" type="tip">
  <p>
    In a perfect world, every translation key would be fully typed. In practice, the i18n object is large enough that TypeScript's union type inference struggles with it. The <code>as any</code> cast is scoped to the component level and does not leak. If a key is wrong, it will show <code>undefined</code> in the rendered UI, which is caught immediately during development or in Storybook.
  </p>
</DesignDecision>

## Adding a New Language

To add a third language (e.g., Farsi, Hebrew, Urdu), the process is:

1. Add a new top-level key to the `content` object (e.g., `fa` for Farsi).
2. Replicate the **exact same key structure** as `en` and `ar`. Every key that exists in English must exist in the new language.
3. Update the `locale` type in `DirectionProvider` to include the new locale.
4. Update `useDirection()` to handle the new locale's direction (Farsi is RTL, like Arabic).

<CodeBlock
  filename="Adding Farsi (hypothetical)"
  language="typescript"
  code={`export const content = {
  en: { navigation: { home: 'Home' } },
  ar: { navigation: { home: 'الرئيسية' } },
  fa: { navigation: { home: 'خانه' } },  // Same keys, Farsi values
};`}
/>

The key constraint is **structural symmetry**: all language branches must have identical key paths. Missing keys will produce `undefined` at runtime.

## The JSONB Strategy

The i18n system described above handles **UI strings** -- labels, buttons, descriptions, and status messages that are part of the application chrome. For **user-generated content** stored in a database (e.g., product names, article titles, user bios), NoorUI recommends a JSONB column strategy.

Instead of separate columns per language (`title_en`, `title_ar`), use a single JSONB column:

<CodeBlock
  filename="Database schema (JSONB approach)"
  language="sql"
  code={`CREATE TABLE products (
  id UUID PRIMARY KEY,
  title JSONB NOT NULL DEFAULT '{}',
  -- title: { "en": "Wireless Headphones", "ar": "سماعات لاسلكية" }
  description JSONB NOT NULL DEFAULT '{}',
  created_at TIMESTAMPTZ DEFAULT NOW()
);`}
/>

This approach scales to any number of languages without schema changes and supports partial translations (a product might have an English title but no Arabic description yet). The full strategy, including translation tracking and fallback behavior, is documented in `MULTILINGUAL_STRATEGY.md`.

## File Structure Considerations

<DesignDecision title="Single file vs split files">
  <p>
    The current single-file approach (<code>lib/i18n.ts</code>) was chosen for simplicity: one import, one object, one place to search. For a two-language library with ~6000 lines, this is manageable. If NoorUI expands to 5+ languages or the file exceeds ~15K lines, splitting into per-language files (<code>lib/i18n/en.ts</code>, <code>lib/i18n/ar.ts</code>) with a shared type definition would be the natural next step. The consumer API (<code>content[locale]</code>) would remain unchanged.
  </p>
</DesignDecision>
